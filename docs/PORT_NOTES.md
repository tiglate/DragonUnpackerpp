# Notes of the port (history)

> Historical notes written while the program was ported, first to Free Pascal and then to C++20. The names of units (`drv_fmt_*.pas`, `drv_*.pas`) are the old Pascal ones: the C++ file of the same format is in `driver/cpp/src/formats/` or `codecs/` (`git log` has the Pascal). The current status is in `MIGRATION.md`; this file keeps the technical findings (layouts worked out from real files, what was checked and how).


Goal: compile and run Dragon UnPACKer on Linux 64-bit with Lazarus (v6 code base in `DragonUnPACKerLazarus/`), keeping the v5 Delphi code base building.
`CLAUDE.md` describes the architecture and how to build/test; this file tracks **what is done and what is left**. Update it whenever an item is started, finished or discovered.

Legend: [x] done, [~] in progress, [ ] pending.

## C++ port of the driver (started 2026-10-27, finished 2026-10-28)

**Status: done.** All 97 formats run in C++ (`driver/cpp`); the Pascal driver, its host (`dudi7host`), `dudi7cli.lpr`, the Lazarus project and the lazbuild/fpc steps were removed in the "C++ driver: switch over" commit (the last commit that still has them is its parent; `build/plugins/` now holds the C++ plugin, `build/tools/dudi7cli` is the C++ test tool, `./make.sh test-driver` and `test-ui` pass). The text below is the history of the port: the Pascal-versus-C++ comparison scripts (`compare_cpp.sh`, `fuzz_compare.py`) no longer exist. Remaining: the Windows build (never compiled, see Known issues).

Goal: the whole driver in modern C++20 (`driver/cpp/`, like the Qt interface), with the same DUDI 7 C ABI, so that the Pascal sources (`driver/src`, `driver/host`, `driver/tools`) and `lazbuild`/`fpc` can be dropped. The two plugins live side by side until parity: `build/plugins/` (Pascal) and `build/plugins-cpp/` (C++, `./make.sh build cpp`).

Method: each Pascal unit becomes one file in `driver/cpp/src/formats/`, ported literally (same checks, same limits, same names and data_x/data_y), then added to `driver/cpp/src/FormatList.inc` **at the position of the unit in `drv_default.lpr`** (the order decides which format claims a file). `./make.sh test-cpp` must stay green:
- `driver/tests/compare_cpp.sh`: every fixture (or every file of a directory, e.g. copies of real archives) is listed and extracted through both plugins with `dudi7cli`: names, offsets, sizes and MD5 must be identical; `dump.c` also compares what `dudi7cli` hides (directory separator, `extract_internal`, `data_x`/`data_y`, the table of formats, which must be a subsequence of the Pascal one with the same texts). The fixtures only the Pascal driver knows must be exactly the ones of `cpp_todo.expected` (`CPP_TODO_UPDATE=1` rewrites it when a format is ported).
- `driver/tests/fuzz_compare.py`: the mutated fixtures of the ported formats must give the same listing or the same status code in both.
- `DUDI7_PLUGIN=build/plugins-cpp/libdrv_default.d6d.so driver/tests/run.sh` (and `run_all.sh`) run the C harness, the Pascal host test and the independent references (`verify_*.py`, `unity_ref.py`, ...) against the C++ plugin.

- `drv_fmt_unityfs.pas` (+ `drv_lz4.pas`, reusing `drv_lzma.pas`): UnityFS bundles, format versions 6/7/8 (Unity 2018 to 2021, Unity 6). Entries are the files of the bundle (`CAB-xxx` serialized files and `.resS`/`.resource` streams, extracted raw) followed by the assets inside the serialized files, see the next section.

### Session notes: Unity serialized files (textures, sounds, texts, fonts)
- `drv_unity_serial.pas`: reader of the serialized files (the `CAB-*` nodes with flag 4, or any other node that is not a `.resS`/`.resource` stream: the header decides), versions 17 to 22 (Unity 2017.x to Unity 6), little endian, with type trees (every Addressables/asset bundle of the library has them; the player data of release builds does not, see below). It reads the types (flat node lists, texts from the node's string table or from the table of common texts) and the object table, and reads the fields of an object by walking its type tree (arrays, strings, alignment on 4 bytes relative to the start of the object after nodes with flag 0x4000). Only blobs' positions are kept, never the payloads, so a 53 MB serialized file is not loaded in memory. `drv_unity_export.pas`: what the objects become on extraction.
- For each serialized file, `drv_fmt_unityfs.pas` adds `CAB-xxx.objects/<Class>/<name><ext>` entries after the raw ones, for Texture2D, TextAsset, AudioClip and Font. Duplicated names get `_<pathid>`. A serialized file that cannot be read (no type tree, other version, damaged) is silently left raw: it never makes the bundle fail to open.
- Textures: data from `m_StreamData` (path resolved to the `.resS` node of the bundle by its last path part, offset, size) or inline `image data`. Alpha8/R8, RGB24, RGBA32, ARGB32, BGRA32 become 8/24/32 bits TGA (bottom-left origin like Unity: no flip, pixels swizzled); DXT1, DXT5, BC4, BC5, BC6H, BC7 become DDS (BC6H/BC7 with a DX10 header), first mip level only, rows stored bottom first as in Unity so DDS viewers show them upside down (BC7 blocks cannot be flipped losslessly); any other format (ETC/ETC2/ASTC/PVRTC/crunched/float/16 bits, or data shorter than width x height needs) is extracted raw as `<name>.<family>.bin`. Sounds are the bytes of the `m_Resource` range of the `.resource` stream (FSB5 banks: `.fsb`, nothing is decoded); texts are `m_Script` (`.json`/`.xml`/`.txt`/`.bytes` guessed from the content); fonts are `m_FontData` (`.ttf`/`.otf`).
- Tests: `tests/dudi7/unity_ref.py` is an independent python reader (own tree walker, naming, TGA/DDS builders) that lists a bundle's files and objects with the MD5 of each; `verify_real.py` compares the driver with it (names, sizes, MD5, and the CLI itself reports any difference between the listed size and the bytes extracted). Synthetic bundles `obj17/obj22/obj22c/ufs22.bundle` (hand built type trees, v17 and v22, local and common texts, a stripped-tree CAB, duplicated names, every texture family) are in `run_all.sh` and the harness; the fuzzer mutates them too. Pillow was used once to decode the extracted TGA/DDS files and check the pixels (orientation, ARGB swizzle).
- Real-file coverage: serialized versions 17 (Overcooked 2, Metal Unit), 21 (Huntdown) and 22 (Silksong, Skul, Chained Echoes, Blasphemous 2, Vigil, TOI) were compared with `unity_ref.py` (152 `.bundle` files of six games + 32 extensionless bundles: names, sizes and MD5 of every file and object, all equal); version 19 only appears once in a census of 150 more files (not compared) and in the synthetic `obj19.bundle`. `tests/dudi7/unity_stats.py` counts what the reference leaves out and why: over those 150 files nothing was left out (2,829 textures, 144 texts, 592 sounds listed, no unreadable serialized file or object). The driver lists all 5,701 Unity files of the library without a single failure (73,358 object entries, 250 bundles listed in under 4 s). 44 extracted sounds are valid FSB5 files whose internal length equals the extracted size; real textures were converted with Pillow and looked at (upright, right colors, BC7 through the DX10 header).
- **Serialized files without type trees** (the player data of release builds: `data.unity3d` of Ara Fell/Math Ultra, `globalgamemanagers`, `sharedassets*.assets`, `resources.assets`, `levelN`; Unity 2019.3, version 21) are read with built-in layouts. `tests/dudi7/unity_trees.json` holds the real type trees of Texture2D (Unity 2018.4, 2019.4, 2020.3-2021.3, Unity 6), AudioClip (2), TextAsset and Font, harvested from the files of the library that still have them; `gen_unity_trees.py` turns them into `drv_unity_trees.pas`. For such a file `TUnitySerialized.ReadObject` tries every layout of the class and keeps the first one that reads exactly the whole object **and** gives plausible values (texture size 1..32768, format 1..64, `m_CompleteImageSize` = inline data + streamed size; sound size and channels): reading the right number of bytes alone is not enough, a layout of another version once matched and gave a wrong format. Type dependencies (version 21+) are only in the metadata when there are trees. Verified by forcing the layouts on files that have trees (`DUDI7_UNITY_TEMPLATES=1` test hook): the listing was identical on 7,737 Unity files of the library; and against `unity_ref.py` on Math Ultra/Ara Fell. A Unity version whose layout is not in the json is listed raw (add a real tree to the json to cover it).
- Standalone serialized files (`drv_fmt_unityassets.pas`, extension `.assets` and any file whose header is consistent: version 17-22, size field = file size, readable type and object tables; `levelN`/`globalgamemanagers` have no extension) list `objects/<Class>/<name>` only; the `.resS`/`.resource` data streams are the files of the same folder (case-insensitive lookup), positions carry the source number in bits 40+ (`drv_unity_objects.pas` is the part shared with the bundles). Checked against `unity_ref.expected_assets` in place (nothing copied) on the `.assets`/`levelN` files of the library.
- Not done: the ETC variants of crunch, PVRTC, Texture2DArray/Video objects, SpriteAtlas, skinning/blend shapes/compressed meshes, big endian serialized files, Unity versions whose layouts are not in `unity_trees.json` (2022.x Texture2D without trees, etc.).


### Session notes: FMOD banks (`drv_fmt_fmod.pas`)
- FSB5 (`.fsb`, and the `.resource` streams of Unity sounds) and FMOD Studio banks (`.bank`: RIFF "FEV ", the FSB5 is in the `SND ` chunk after some padding; the `LIST` chunk with the events is not read; Master/strings banks have no sounds and open with 0 entries). Entries are the samples, named from the names table (`sample_NNNNN` without one, duplicates get `_<index>`). PCM (8/16/24/32/float) gets a WAV header, MPEG is a valid `.mp3` (the first frame of the short ones can trip ffmpeg's seek: the data is padded to 32 bytes in the bank), every other codec (ADPCM, XMA, CELT...; Vorbis and MPEG are converted, see the next notes) is given raw as `<name>.<codec>.bin`. A sample's size is the distance to the next sample *by position* (positions are not increasing in banks), so it includes the padding up to 32 bytes.
- Not done: FSB4 (no sample in the library), decoding/converting the raw codecs, the event/bus data of the banks (names of events from the `.strings.bank`).
- Checked: the 88 `.fsb`/`.bank` files of the library (64 FSB5 + 24 banks) against `verify_real.py` (own parser: names, offsets, sizes, MD5), PCM output decoded by ffprobe; fixtures `test.fsb`, `mpeg.fsb`, `test.bank` (unsorted positions, extra frequency chunk, duplicate names), `empty.bank`.

### Session notes: XNA content files (`drv_fmt_xnb.pas`, `drv_lzx.pas`)
- `.xnb` (XNA 3.1/4, MonoGame): one object per file, so one entry named after the file. Texture2D (version 5): Color/565/5551/4444/Alpha8 -> TGA (top-left origin, no flip), DXT1/3/5 -> DDS (first mip; XNA rows are top first so the DDS is upright, unlike Unity); SoundEffect -> WAV (the file's own format block: PCM, MS ADPCM...); Effect -> `.fxb`; anything else (SpriteFont, custom readers, Video) -> the unpacked content as `<name>.<type>.bin`. Compressed files (flag 0x80 LZX, 0x40 LZ4 of recent MonoGame) are unpacked in memory at open.
- `drv_lzx.pas`: LZX decoder (64 KB window, XNA chunk framing, verbatim/aligned/uncompressed blocks, E8 translation), written from the libmspack description. No LZX compressor exists here, so: all 410 LZX-compressed XNBs of the library (Owlboy, Dust, Chasm) unpack to content whose structure is exactly consistent (texture byte count = width x height x bits per pixel, fxb/spritefont parse) and the images decode and look right (checked visually); the fixtures only cover stored blocks and chunk framing. The bit reader restarts at each chunk (the encoder pads every chunk to 16 bits).
- Checked: all 4,629 `.xnb` of the library open (3,652 of them in a folder with a non-ASCII name); 1,367 of a random 1,500 compared with an independent python converter (name, size, MD5; the others are the LZX ones). Not done: version 4 (XNA 3.1) texture formats (listed raw), Video conversion, texture mip levels beyond the first.
- Bug found on the way: the driver could not open files whose path has non-ASCII characters (`EFOpenError ... Illegal byte sequence`; the library was missing `cwstring`, so UTF-8 paths were converted as if they were ASCII). `drv_default.lpr` now uses `cwstring` on Unix. Worth a test of the GUI with such a folder.

### Session notes: crunched, ETC/EAC, ASTC and 16 bits Unity textures
- Library census before this work: of the Texture2D objects that were left raw, 6,875 were crunched (DXT1/DXT5 crunch: Teslagrad 1+2, Chained Echoes, Silksong, Math Ultra), 21 ARGB4444 and 1 float; there is **no ETC, ASTC or PVRTC texture in the library** (desktop games). They were done anyway and checked against an independent decoder on random data.
- `drv_crunch.pas`: Unity crunch (DXT1 = format 28, DXT5 = 29), ported from the decoder of Unity's crunch fork (zlib license, see the header of the unit) as read in the texture2ddecoder package. Extracted as DDS (level 0, same bottom-first rows as the other Unity DXT textures). Checked: the blocks are identical to `texture2ddecoder.unpack_unity_crunch` on 107 real crunched textures (103 DXT5, 4 DXT1; all their mip levels), on 10 random real `.assets`/bundles end to end, and on files made by `tests/dudi7/crunch_enc.py` (a small non compressing encoder written for the fixtures). Not done: the ETC variants (formats 64/65: no sample, the encoder could not be built here, so they stay raw `.crunch.bin`), DXT3/DXN/DXT5A crunch, and level > 0.
- `drv_texdecode.pas` (ETC1, ETC2 RGB/RGBA1/RGBA8, EAC R/RG signed or not: formats 34, 41-47, 60, 61) and `drv_astc.pas` (ASTC 4x4 to 12x12, LDR and HDR: 48-59, 66-71) decode to 32 bits TGA (bottom-left origin like the other Unity textures). Checked on random blocks against texture2ddecoder: ETC/EAC byte for byte on 64 images (all modes: individual, differential, T, H, planar, punch-through, EAC), ASTC on about 21,000 random valid blocks plus void extents, partitions, dual plane and HDR endpoint modes. The ASTC blocks that are not valid (reserved modes, more weights than fit...) become the magenta error color; the reference reads out of its buffers on those and cannot be compared.
- ARGB4444, RGBA4444 (-> 32 bits TGA) and RGB565 (-> 24 bits) were checked on a real texture (Chained Echoes) and on fixtures. Still raw: PVRTC, ATC, R16/RG16, float and half textures, RGB9e5, BC6H/BC7 are DDS as before.
- Tests: fixture `texfmts.bundle` (every format above, 22 entries); `verify_real.py` compares it with `unity_ref.py`, which uses texture2ddecoder when it can import it (`pip install texture2ddecoder`, or `TEXTURE2DDECODER_PATH`) and otherwise only compares names and sizes; `texfmts.expected` keeps the MD5s that the reference agreed with, so `run_all.sh` catches regressions without the package. `verify_texdecode.sh` (optional, skipped without the package) builds `texdec_dump`/`crn_dump` and runs the random comparisons.

### Session notes: XNA SpriteFont
- A `SpriteFontReader` file (version 5) gives two entries: the atlas (`<name>.tga`/`.dds`, the embedded Texture2D, first mip) and `<name>.fnt`, a BMFont text description generated from the font: one `char` line per glyph with the atlas rectangle, `xoffset` = cropping x + left bearing, `yoffset` = cropping y, `xadvance` = left bearing + width + right bearing + spacing (rounded), `lineHeight`/`base` = the line spacing. Layout (checked on the 9 uncompressed fonts of the library, which parse exactly to the end of the file): texture object, `List<Rectangle>` glyphs, `List<Rectangle>` cropping, `List<char>` characters (UTF-8 chars as .NET BinaryReader writes them), line spacing (int), spacing (float), `List<Vector3>` kerning (A, B, C per glyph), default character (a bool then the char, inline: no type id).
- Checked: all 16 fonts of the library convert (7 are LZX compressed: Dust), the 9 uncompressed ones against an independent parser (`verify_real.py`: names, sizes, MD5 of the atlas and of the `.fnt`); a rendering of "Hello, World!" from the `.fnt` + atlas of Dust's Arial (compressed, DXT) with Pillow is correct. Fixtures `font.xnb` / `font_lzx.xnb`. Not done: the XNA kerning is per glyph, not per pair, so the `.fnt` has no `kerning` lines; the default character is not exported.
- Found on the way: many XNB files (Chasm) have a size field in the header that is smaller than the file; the content of uncompressed files now runs to the end of the file (MonoGame ignores that field too).

### Session notes: playable FMOD sounds (Vorbis, MPEG, exact PCM)
- **Vorbis (codec 15) -> `.ogg`**: FSB5 keeps only the audio packets (16 bits size + packet); the setup header is replaced by the CRC32 of one of 161 setup packets that come from FMOD (`drv_fsb_codebooks.pas`, generated by `tests/dudi7/gen_fsb_codebooks.py` from vgmstream's `vorbis_codebooks_fsb.h`, ISC; python-fsb5 extracted them; stored zlib compressed, 172 KB; `fsb_codebooks.zlib` is the same data for the python reference). `drv_vorbis_ogg.pas` builds the identification header (blocksizes always 256 / 2048), an empty comment header, parses the whole setup header to get the blockflag of every mode (a first attempt that scanned backwards from the framing bit found wrong modes: do not do that; the setup depends on the number of channels because of the coupling steps), and writes the Ogg pages with granule positions; the last page is the number of samples of the sound so the padding is cut. The size announced when the bank is opened comes from a dry run that only walks the packet sizes (3,572 sounds of a 178 MB bank open in 0.4 s). A sound with an unknown CRC, several layers (extra chunk 14) or an invalid setup stays `<name>.vorbis.bin`.
- **MPEG (codec 11) -> `.mp3`**: FMOD pads every Layer III frame to 4 bytes (16 for more than two channels, i.e. several interleaved stereo streams): the frames are written one after the other without the padding (the entry size is the sum of the frames). More than 2 channels: left raw as `.mpeg.bin` (interleaved streams, not a playable file; 15 sounds in Shovel Knight's music.fsb).
- **PCM -> `.wav`**: the data is cut to samples x channels x bytes (the FSB pads every sound to 32 bytes). The channel count of the 2 bit field of the sample header is 1/2/6/8 (it was read as 1..4: bug fixed).
- Checked on the library: 21 banks of Tails of Iron, Unsighted and Celeste: every one of their 11,000+ sounds is an `.ogg` (all CRCs are in the table); 478 sounds picked in all of them (and 120 in NPC_Bank) decode with ffmpeg without a single error and with the exact duration (samples / rate); 5 banks/fsb (UI_Bank, ui, dlc_music, specter, music) are byte for byte what the independent python implementation (`fsb_ref.py`, own setup parser and Ogg writer, via `verify_real.py`) builds. MPEG: 3,781 sounds of the 64 `.fsb` decode without error; durations match (only the 15 multichannel ones, now raw, did not). Fixtures `vorbis.fsb`, `vorbis.bank`, `mpeg.fsb`, `test.fsb` (PCM).
- Not done: the other codecs stay raw (IMA ADPCM, GC ADPCM, VAG, XMA, CELT, AT9, XWMA, FADPCM, Opus: no sample in the library, nothing to check them with), multichannel MPEG and Vorbis layers, FSB4. The `fsb_codebooks` table only covers the setups known to vgmstream: a new FMOD version can add some.

### Session notes: Unity Cubemap, Sprite and Mesh objects
- The three classes were the biggest unexploited objects of the library: **351,527 Sprite entries** (Chained Echoes 140,000, Blasphemous 2 70,000, Ara Fell 48,000...), **22,895 Meshes** (Dandara 10,700, Silksong 6,400, Teslagrad 5,300...), 6 cubemap faces; about a third of the sprites and 70% of the meshes are in player data without type trees. The serialized files of the player data have no type trees, so `unity_trees.json` got the real trees of Sprite (2018.4, 2019.4/2020.3, 2021.3, Unity 6), Mesh (2018.4, 2020.3/2021.3, Unity 6) and Cubemap (2019.4), harvested from the bundles of the library with `Plausible` checks (rectangle sizes, pixels to units, vertex count, index format...). A Unity version that has no tree is still read when one of the others has the same layout; Meshes of 2017/2019.x player data are the likely gaps (no sample of their tree).
- `TUnitySerialized` now keeps the first 64 elements of the arrays of structures (`m_SubMeshes[3].indexCount`, `m_VertexData.m_Channels[0].stream`), `FloatOf` and `UnityVersion/UnityMajor`. A bundle whose serialized files say 0.0.0 (Silksong strips the version) uses the engine version of the bundle header, then the serialized version to choose between the vertex format numberings (2018 / 2019+).
- **Sprite -> `Sprite/<name>.tga`**: the rectangle `m_RD.textureRect` of the texture `m_RD.texture` of the same file, as a 32 bits TGA (bottom line first, like the textures). The pixels come from uncompressed formats (Alpha8 is white + alpha, R8 gray, RGB24, RGBA32, ARGB32, BGRA32, 4444, 565), DXT1/DXT5 (new BC1/BC3 decoders in `drv_texdecode.pas`, checked against texture2ddecoder like the ETC/ASTC ones), crunched DXT (the atlas is unpacked once and kept for the next sprite), ETC/EAC and ASTC; only the rows of blocks that the sprite covers are decoded. Sprites that refer to a texture of another file (m_FileID <> 0), of an unsupported format or outside of the texture are not listed. Not done: the polygon mesh of tight sprites (the rectangle is exported whole), the alpha texture, SpriteAtlas objects.
- **Cubemap -> `Cubemap/<name>_px|nx|py|ny|pz|nz`**: the first mip level of each of the 6 faces (m_CompleteImageSize is the size of one face with all its mips), as TGA/DDS like a Texture2D.
- **Mesh -> `Mesh/<name>.obj`** (`drv_unity_mesh.pas`): positions, normals, first UV set and one `g subN` group per triangle submesh (triangle lists, strips and quads; lines and points are skipped). x is negated and the faces reversed (Unity is left handed). The size of the file is computed without writing it, so the numbers are printed in fixed 13 character fields with 6 decimals (|value| clamped to 99999.999999) and the indexes are zero padded to the digits of the vertex count: valid OBJ, a bit verbose. Unity 2018 and later (14 channels), uncompressed, up to 2,000,000 vertices.
- Checked: the driver lists the 7,394 Unity files of the library without a failure (the counts above); 19 random bundles (Chained Echoes, Blasphemous 2, Metal Unit, Skul, Silksong) and 29 random player-data files (17 games, Unity 2017 to 6000, with and without trees) are identical to the independent reader `unity_ref.py` (its own tree walker, BC/ETC/ASTC decoding through texture2ddecoder, sprite crop, OBJ writer); a rendering of the radial mesh of Silksong's `Circle` looks right. Fixtures `objs3.bundle` (with trees) and `objs3_notree.bundle` (layouts found from the real trees): atlas + DXT1 texture, sprites that cut them (one refers to a missing texture), cubemap, two meshes (floats with normals and uv; half float positions, 32 bits strip with a base vertex).

### Session notes: opening time of big Unity bundles
- Found by opening Ara Fell's `data.unity3d` (300 MB LZMA, 2.2 GB of `resources.assets` with 48,000 sprites): the sprite pass needed almost every block, 3 minutes at about 10 MB/s of LZMA output (the Pascal decoder runs at 20-25 MB/s on poorly compressible data, liblzma at 70; a version with the range decoder in a record, inlined, and one with local variables in the literal loop were tried and gave nothing, the original is kept). Fixes: the objects of the second pass are read in the order of their data and the entries added afterwards in the order of the table (no seeking back), a 4 block cache (an object that straddles two blocks no longer unpacks the same block twice), growth by chunks of the entry records (`SetLength(+1)` of a 250 byte record per entry was quadratic), a texture is looked up once per sprite atlas, the layout of a stripped object that worked last is tried first, arrays of fixed size structures that are not wanted (points of a physics shape) are skipped as a block.
- Guard: when the second pass (Cubemap/Sprite/Mesh) of a serialized file would have to unpack more than 256 MB of a packed bundle, it is not done (the listing then has the other objects only; Ara Fell opens in 0.6 s instead of 3 minutes). `DUDI7_UNITY_DEEP=1` in the environment of the driver lifts the limit. A progress callback (DUDI host callbacks exist but the default driver does not use them) would be the proper fix.

## The end of the port: legacy/ and the Pascal files removed

Everything of v5 that made sense is in the C++ driver and the Qt interface: the 126 formats, HyperRipper (with HRF files and naming), the converters (`cnv_pictex`, `cnv_exttools`), the list templates (DUHT), the Unreal packages, the translations (made again, in 11 languages) and a file type detector that v5 did not have. What was left behind on purpose, and where to find it (`git show legacy-v5:<path>`):

- The 11th Hour GJD needs `drv_default_d11d.dat`, built from the CD with `tools/d11dc`; Worms Armageddon DIR was never working in v5.
- The small tools `dlngc`/`dlngcomp`/`dlngd` (language files of v5), `dlookc`/`dlookd` (themes), `dpackc`, `duppi`, `fngen`, `dus`: they belong to the plugin, theme and language systems of v5 that the Qt interface does not have.
- The installer script `install/setup.iss` (Inno Setup), a reference for a Windows installer.
- HyperRipper reading HRF version 0 files, and its multi-thread scan (disabled in v5 too).
- The history files (`docs/core/whatsnew.txt`, `historique.txt`) and the language files of v5 (`translations/`).

Kept from `legacy/`: the specification of the HRF files and the documentation of DUHTComp (`docs/formats/`), and the list of the names of the Westwood MIX files (`driver/data/mix_names.lst`, the source of `codecs/MixNames.data.inc`). The Pascal contract `spec_DUDI7.pas` became `driver/contract/DUDI7.md`.
