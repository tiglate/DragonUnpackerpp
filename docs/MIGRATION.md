# Dragon UnPACKer++: status of the port

Dragon UnPACKer++ is the port of Dragon UnPACKer 5 (Delphi 7, by Alexandre "Elbereth" Devilliers) to C++20 and Qt 6, with new features. `CLAUDE.md` describes the architecture and how to build and test; this file says **what is done and what is left**. Keep it updated.

The technical notes written during the port (layouts worked out from real files, what was checked and how) are in [`PORT_NOTES.md`](PORT_NOTES.md); the formats that still need a real file are in [`FORMATS_TO_VALIDATE.md`](FORMATS_TO_VALIDATE.md); the design of the interface is in [`UI_REDESIGN.md`](UI_REDESIGN.md).

## Done

- **Driver** (`driver/`, C++20, plain C ABI "DUDI 7", rules in `driver/contract/DUDI7.md`): 135 formats, all of v5 except the two below, plus formats that v5 did not have (Unity bundles and serialized files, FMOD, XNA, XACT, GameMaker, Unreal PAK and packages, Godot PCK, Chromium PAK, LFD, Moto Racer 2 BKF, Heroes 4 H4R...). Tested with a fixture per format, fuzzing, a false positive sweep and, for the formats marked as validated, real files.
- **Interface** (`app/`, Qt 6): browsing, previews, extraction as jobs, thumbnails, search, themes, command line hooks.
- **HyperRipper**: the 27 types of v5, MP3/AAC options, naming templates, HRF files (versions 1, 2, 3), statistics.
- **Converters** (`cnv_pictex`, `cnv_exttools`), **list templates** (DUHT), **translations** (11 languages, right to left included).
- **New**: file type identification from the content (`Core/FileTypes`).
- **Packaging**: `./make.sh install` and `package` (tarball with desktop file and icons).
- The Delphi sources (`legacy/v5/`) were removed once everything that made sense was ported: git tag `legacy-v5`.

- **Requiem: Avenging Angel** (`RequiemArt.cpp`, `RequiemJam.cpp`, `codecs/Dcl`; found by reading the game's own loader in `3DFX.exe` with Ghidra, no public documentation): the textures (`Art/{SW,HW,D3D}/*.art` + `.dat`) and the levels (`Maps/*.jam`, `levels.dat`) are PKWARE DCL ("implode") streams: `Dcl` is written from the public description of that format. Textures: `.dat` = one u32 offset per slot (0xFFFFFFFF or 0 = empty; slots are not in file order), `.art` records = unpacked size, 0, packed size (counts itself), DCL stream; the texture is an 18 byte header (w, h, mip levels at byte 13, bytes per pixel at byte 14: 1 = palette index, 2 = index + alpha), a 256 x BGRA palette (D3D set only), the pixels (all the mips in the SW set), 112 bytes of renderer data (HW set). Entries are TGA pictures (rows bottom first, first mip level only). D3D: 32 bits in colour with the alpha channel. HW: the 112 bytes after the pixels are a 3dfx Glide NCC table (16 Y bytes, 4 x 3 signed 9 bits I and Q values, the same again packed in 12 words) and each pixel byte is YYYYIIQQ: colour = Y + I + Q per channel, clamped (checked against the D3D set: mean error 3.6 of 255, quantisation noise); with 2 bytes per pixel the second one is the alpha. SW: pixels are indices into the level palette, which is not in the art files: it is in the second packed block of the `.jam` files (the field at offset 4 of the header is the offset, minus 12, of a u32 unpacked size followed by a DCL stream; the unpacked data starts with 0x0BEAF0CC at offset 4 and holds two tables of 256 RGBX colours at 0x1F and 0x41F, found by reading `PaletteEffects::LoadFromJAM`; the second one is the art's, which was confirmed by averaging the D3D colour under each SW index over the whole set: mean difference 11 of 255). 79 of the 83 level files have the same palette (`tower2`, `tower3`, `torture` and `Guerni~3` have another one): the art archive looks for `Maps/*.jam` above its folder and takes the palette that most of the first 9 have (colour mapped TGA, so the preview palette can still be replaced; grays when there is no Maps folder). All 8049 records of the three sets unpack to exactly their stored size. Levels: magic 0xFEED000A, unpacked size at 8, version at 16 (0, 1 or 2), then a u32 packed size + DCL stream at 0x112 + version * 0x100C; entries `header.bin`, `level.bin` (first unpacked block), `rest.bin` (after it, not compressed, holds the second block), `data.bin` (second block, unpacked: the level data proper) and `palette.pal` (768 bytes RGB, which the interface uses for the pictures of the same archive), and `level.gltf`, the geometry of the level (`codecs/RequiemLevel`; read from `LoadJAM` at 0x4606E0 of `3DFX.exe` and the renderer, layouts in the header comment): `data.bin` is a memory image of the game's objects, loaded at 0x06000000 (every pointer is 0x06000000 + an offset into the block); the u32 at 0 is the size of a trailer that lists the objects by class (count + pointers per class number, ending exactly at the end of the block); class 3 objects with vertices are the geometry (vertices at +0x40, counts at +0x44/+0x46, faces of 0x68 bytes at +0x48), class 108 objects the textures (art slot at 0); each face is cut along the borders of its texture repeats into pieces that carry the texture coordinates (texels of the software set, the same sizes in the D3D set), and those pieces are what is drawn (the glTF has one primitive per texture, `artSlot` in the material extras, texels / 128 with V negated so it repeats into the right row whatever the height; slots above 4000 are made by the game at run time and have `gameTexture` in place of a slot). All 83 level files of the game (the 82 `.jam` and `levels.dat`) list and extract their `level.gltf` (dm1: 39 objects, 8275 polygons; the largest, sewer2, 39,615 triangles, 4.7 MB of glTF, 0.06 s to list, previewed in the app); checked by drawing them (the layout of dm1 from above, the walls with their dirt at the bottom), by `tests/verify_requiem.py` on the `req_v*.jam` fixtures, and by mutating the unpacked block of the fixture (400 runs, no crash). The in-app viewer reads glTF files of several primitives as parts, each with its picture. Lightmaps (read from `InitTexCache` at 0x4F6160 and `MarkPolyForUse`; layout in the header comment of `codecs/RequiemLevel.cpp`): the u32 at 12 of the header is their count, `level.bin` holds their samples (RGB555, at most 16 x 16) and the count entries of 12 bytes at the start of `rest.bin` describe them (s0, t0, width, height, offset); a piece names its lightmap (u16 at +0x18) and the lighting frame of its face (origin and two axes, about one sample per unit, tiles of 15 samples) places its corners in it. `level.gltf` packs them in one picture (cells of 18 x 18 with a border, PNG in the buffer) given to every material as the occlusion texture with TEXCOORD_1 (standard viewers show it as occlusion, in gray); the in-app viewer multiplies the textures by it (bilinear, 1x: the game's dark look), L switches it off. Checked by the continuity of the lighting where the pieces of a face meet (exactly equal on dm1 and newpp2; flipped or transposed lightmaps differ by 1 to 2.6 levels of 31), on all 83 level files, and by the colours of the fixture (`verify_requiem.py`, `test_rig.cpp`). Listing a level takes 0.2 to 0.35 s with the atlas (0.06 s without). All 83 real files open and unpack. Animation pack (`RequiemAnim.cpp`): `Models/AnimFile.ary` (u32 count, then 16 byte records: offset, 0, size, 0xCDCDCDCD) + `AnimFile.bin` (the 499 records, contiguous, fill the file); `AnimFile.tab` (5120 u16, model id * 40 + animation number to record, 0xFFFF = none). Records are listed raw (`anim_NNN.bin`, same layout as the `.ani` files, see below; with `AnimFile.tab` and `Models3.txt` next to the pack they are `raw/NNN_<animation>.ani`, named by the first line that lists them: 498 of the 499 are named); when `AnimFile.tab` and `Models3.txt` are next to the pack, each animation of an `M` model is also shown on its model as `<model>/<animation>.gltf` (the model's glTF with that animation alone; an animation that does not fit the limbs is left out, a name used twice in a folder gets `_<id>_<n>`). The glTFs are built once in `Parse` for their size and again on extraction (one `GltfBuilder` per model keeps the mesh part), not kept in memory. On the game: 499 records plus 713 glTFs for the 68 `M` models (listing 0.4 s, 15 MB), every one equal to the same animation in the model's own glTF; the 10 animation lines of `Models3.txt` without a glTF point to a record of another skeleton (e.g. `civm1threat` under `RL.mdl`). A record that no line shows on a model goes to the only model file of the folder with its limb count, when there is exactly one: the five `tsf*.ani` that `Models3.txt` lists under `TortFemale.mdl` (11 limbs) have 13 limbs, and `ts4.mdl` is the only 13 limb model, so they are shown on it (the poses are coherent: an upright figure, arms raised); `ts7fullhang` and record 498 have 18 limbs, which five different skeletons have, and stay raw only (718 glTFs in all). Two records (50 and 51, `civthrash3` and `civthrash2`) hold the 0xCDCDCDCD fill of the tool that wrote them (the MSVC debug runtime) in place of the constant position of the root limb: the sampler takes it as no position (the model would be 431 million units away otherwise); the `filled.ani` record of the fixture checks it. The model code is shared by both formats in `codecs/RequiemModel.{h,cpp}`; `tests/verify_requiem.py` checks the pack against the model's own glTF on the `req_pack/` fixtures. Models (`RequiemMdl.cpp`; read from the game's loaders at 0x441E90 and 0x41F5F0-0x41F950; layouts in the header comment of `codecs/RequiemModel.cpp`; all 150 `Models/*.mdl` parse byte for byte, 62 static and 88 skeletal): shown as OBJ + MTL (one limb per `g limb_N` group for the skeletal ones; faces keep their texture coordinates, 16.16 fixed point texels, scaled by the smallest power of two >= 32 that holds them since the texture size is not in the file). The vertices of a skeletal model are stored per limb, each in its own space, and posed by an animation (read from the sampler at 0x41E870 and the skeleton walk at 0x41E3F0; layouts in the header comment of `codecs/RequiemModel.cpp`): per limb a rotation (quaternion) and a position, each constant or a spline of cubic polynomials in the frame number, with the flags of 8 limbs per 32 bit word; the skeleton is the depth first order given by the first u32 of the limb records of the model. The animation files (`Models/*.ani`, and the 499 records of `AnimFile.bin`, which are the same files) end exactly where the limbs of their model end, so the limb count that fits is unique and doubles as a check (the `.ani` header does not hold it for most files). The model uses the animation file of its name, else its first animation in `Models3.txt` (record `AnimFile.tab[id * 40 + n]`), else any `.ani` that starts with its name, else the animation of a model with the same skeleton (captain and private borrow the civilian's); the first frame is used. 82 of the 88 skeletal models are posed and also given as `name.gltf` (glTF 2.0, buffer embedded: one joint node per limb with the first animation's first frame as its pose, rigid skinning with the vertices left in limb space and identity inverse bind matrices, one glTF animation per fitting animation of the model, sampled at every frame at 25 per second: translation and rotation channels per limb, constant channels get a single key; verified against the independent Python sampler to 4e-7 and by `tests/verify_requiem.py` with `tests/gltf_ref.py`; the frame rate is assumed, the `.ani` header word that looks like it holds 25.0 in `.ani` files holds other values in AnimFile records); alexis, HandFall, HandFC, HandMC, mojo and oldman have no animation that fits and are exported with every limb at the origin (the OBJ says so in a comment). `tests/verify_requiem.py` checks the pose against hand computed values. The MTL points to `tex_NNNN.tga`, the slot of the art archive given by `Models3.txt` (the `.bmp` name in the model is only a label: Aaron's says alexis.bmp). In-app viewer (`Core/RigModel` + `RigRender` + `Json`, `Ui/RigViewer`, `PreviewKind::RIG`): a `.gltf` entry opens in the Viewer panel as the textured model with a list of its animations, play/pause, a slider and a speed (wheel to zoom at the pointer, drag with the left button to turn, with the right or middle button or Shift + left to move, arrows to move, + and - to zoom, W wireframe, F frame, space play, L lightmaps, H/F1/? for the help of the controls, also in Help > 3D viewer controls; the same controls in the OBJ and Outrage viewers, `Ui/ViewNavigation`); it reads the dialect of the driver's glTF (embedded buffer, skin with identity inverse bind matrices, linear translation/rotation channels), not glTF in general. The picture comes from the art archive of the game: the preview worker looks for `Art/D3D` (then HW, SW) above the folder of the model and extracts `tex_NNNN.tga` (the slot is in the material extras, as is the UV scale: coordinates times it are texels), keeping the art archive open between previews (`ArchiveSource::OpenFile`). Texel V counts from the first stored row of the art TGA (the bottom of the picture): OBJ uses it as it is, glTF as 1 - v (checked on faces and boots of the models). Found on the way: the driver is loaded into the Qt program, whose locale has a decimal comma, and `printf` followed it (invalid JSON, wrong OBJ numbers): the model code now writes numbers with `std::to_chars` and the app reads them with `std::from_chars` (`test_rig.cpp` checks both under a comma locale). Test hooks: `--model-animation=N`, `--model-pose=U`, `--screenshot-delay=MS`. Texture slots (`Models3.txt`): the lines `M` (characters), `G` (guns, with their `F` animations), `N` (network players, `B` animations), `S` (static objects), `I` (items) and `O` (dropped objects) all have `kind id slot file.mdl`; the first non-negative slot of a file is its texture (a file can be listed twice with other slots, e.g. grenade.mdl as S and O: the others are in the glTF material extras as `otherSlots`). Static models are also written as a glTF of one joint without animation, so the viewer shows them textured. 137 of the 150 models have a slot whose picture exists in the D3D art; debris1-3 have slot -1 (no texture in the game) and alexis, captain, hand, hero, mirror, mojo, oldman, phylctry, private and software are not in `Models3.txt` or anywhere else in the game files (the exe has no table either), so they stay untextured. The `T` and `U` lines (alternative skins) are not read. Not done: the pose of the six models above, the skins, the texture size (the UV are scaled by a guess), the tables of 1024 u32 in the headers of version 1 and 2 (their use is not known), the other objects of the levels (lights, sounds, entities), the textures the game makes at run time (slots above 4000), `effects/*.stg`.
- **Descent 3 files** (`app/src/Core/OutrageGraphics`, `OutrageModel`; spec: `docs/file-formats-graphics-and-models.md` of the Descent 3 repository, the source code was not read): `.ogf` (types 121-124 and 127, mip levels, the plain TGA of types 2/10 falls back to `DecodeTga`), `.oaf` (modern and legacy header; the preview shows every frame on a sheet), `.fnt` (monochrome, RGB565 and ARGB4444 glyph sheets) and `.oof` (versions 18.07 to 23.00: subobjects with their offsets applied, textures, gunpoints, batteries and animation tracks parsed; assembled as in the "Assembling and displaying an OOF" section of the spec: unanimated pose, the OHDR detail list is not used, every root is drawn; the viewer leaves out `$shell`/`$frontface`/faceless nodes (and their children, as the game does) as polygons; the OBJ conversion keeps every subobject; the left-handed +Z forward coordinates become right-handed (Z negated, winding reversed) and V is flipped in the OBJ). They are decoded in the interface for preview, thumbnails and "extract with conversion" (PNG / OBJ), not in the driver; `d3.hog` of the Steam/Heroic copy: 2437 OGF, 62 OAF, 7 FNT and 850 OOF all decode. NaN normals of degenerate faces are tolerated (31 models have them), only positions and offsets must be finite. OOF viewer (`Core/OofPose`, `OofRender`, `Ui/ModelViewer`): the preview is a software renderer (orthographic, z-buffer, translucent faces back to front, one-sided faces by the stored normals; `B` shows the back faces, `W` is wireframe) of the model in its unanimated pose or animated: a slider (and a play button, which also turns the `$rotate` subobjects) samples the tracks as the spec says (timed tracks of versions 22 and 23 by tick range, the older ones spread uniformly with the first-interval quirk of the position, keys accumulated as axis-angle rotations, two keys blended by interpolating the nine components and rebuilding Ry·Rx·Rz; `$rotate` and `$fov` turn about the axis of the second key, with one key that key's axis is used and reported). The worked examples of the spec are in `tests/test_oof_pose.cpp`. Textures: the game finds them in its material database (GAM, not read); the viewer looks for `name.ogf` (then the first frame of `name.oaf`) in the same archive: 4185 of the 4343 texture names of `d3.hog` (96%) and 3 more by OAF are found; the others are drawn as a magenta checkerboard, and the note says how many were found. Pixel alpha: texels with no alpha are skipped, partial alpha is blended. Not known without GAM: the texture flags (additive, full-bright, animation speed): animated textures show their first frame, billboards ($facing) are normal blended (a picture with no transparency at all is added, as a flare), the faces are lit with one fixed light (the Gouraud formula of the spec). Effects: `$facing` billboards (half-width sqrt(area)/2 at the origin of the subobject) and `$glow`/`$thruster` as a generated additive gradient, not the game's effect image. The game's cone-shaped glow with external effect state, `$custom`, `$jitter` and the monitors are not drawn. Swept: the 850 models of `d3.hog` at the rest pose and at 0.5 and 1.0, 2550 renders at 800x600 (6.7 ms on average, 51 ms the slowest), no failure and no non-finite value. Not done: OGF type 125/126 (no decoder in the game either), writing the formats, perspective camera, per-key playback speeds from the game's tables. Tests: `app/tests/test_outrage.cpp`.

- **Console ROMs** (`Nes.cpp`, `Snes.cpp`, `MegaDrive.cpp`, shared code in `codecs/RomGfx`): NES, SNES/SFC and Mega Drive/Genesis (also `.smd`) ROMs open as the ROM parts and an info text; the NES CHR ROM (or the PRG ROM of CHR RAM games) is also drawn as tile sheets (TGA, gray: the palettes are in the program). SNES and Mega Drive ROMs are not drawn as raw tiles: most games compress their art and no statistic could tell the few uncompressed areas from compressed data or code (tried: entropy and byte repetition keep about 85% of real tiles and 28% of other data), so the sheets were noise nearly every time. The decoded streams are drawn instead (Mega Drive Kosinski streams only when they are at least 2 KB and a whole number of tiles, since that scheme also packs tilemaps and tables: 1 KB blocks make most of Phantasy Star 4's); a picture stored as tiles in tilemap order (Phantasy Star 4's cutscenes, for example) looks shredded in a 16 tile wide sheet, but the data is right. `codecs/RomCompress` decodes Nemesis and Kosinski and scans Mega Drive ROMs for streams (entries `nemesis/` and `kosinski/`, raw data and sheet), and the Nintendo LZ of the Super Nintendo (`compressed/lz_*`, raw data and 2, 3 or 4 bits sheets; three spellings of the commands: Zelda 3 offsets low byte first, Super Mario World high byte first, Super Metroid (LZ5) with two more copy commands, one with the bits flipped and one from a byte offset back; the ROM keeps the spelling that decodes most streams that use copy commands: counting streams alone is not enough, the wrong spelling decodes a few extra ones by chance; found by scanning at pointer targets and after end markers, kept only in ROMs with a run of abutting streams, which removes the noise of games that do not use it; checked on Zelda 3: 213 streams, mostly the 0x600 byte blocks of that game, and Super Metroid: 268 (its logo, fonts and enemies), and Super Mario World: 53, the 0xC00 byte files, drawn as the real sprites). Tests: `tests/verify_roms.py` (every pixel against an independent decoder, round trips with the encoders of `rom_fixtures.py`). SNES sound: `codecs/Brr` finds BRR samples (the sound chip format; the games copy them as they are to the sound CPU) and extracts them as 32 kHz mono 16 bits WAV (`audio/brr_*.wav`, `_loop` when the last block loops; the loop start and the real pitch live in the sound program, not in the sample). The scan keeps chains of valid blocks that decode like sound (no clipping, smooth, not flat, ranges that change slowly, stored next to other samples or long); Super Mario World gives its 6 samples with no junk. Tested against a reference decoder written separately (`tests/rom_fixtures.py`). Mega Drive sound: `codecs/Pcm` finds the unsigned 8 bits samples that the sound program feeds to the DAC (`audio/pcm_*.wav`, 10 kHz mono 8 bits: the real rate is in the game's sound program). Nothing marks them, so a window of 256 bytes counts when it is centered on 0x80, swings, has steps small next to the swing, turns back and forth at least 8 times (a ramp does not), and does not repeat a value for long (tables and pictures do); runs of such windows of 1 KB or more are samples. Sonic 1 and 2 give their 5 samples near the end of the ROM, Comix Zone about 24 voices and effects (waveforms checked by eye). Music is not extracted: the sequences are driver specific (SMPS and others) and would need the sound CPU to be emulated; the NES has no sampled sound to find in the same way (DPCM and music are code and tables). Palettes: `codecs/Palette` finds them by their structure and lists each as `palettes/pal_XXXXXX.pal` (JASC-PAL) and a swatch picture. Mega Drive colors are words 0000BBB0GGG0RRR0, 16 valid words in a row is a palette (very reliable: on Sonic 1 it finds the level palettes from 0x2280 and the color cycling data). Super Nintendo colors are 15 bits and have a weak signature (a tile map looks the same), so only blocks of 8 lines or more count (tens per game instead of thousands). NES palettes are 16 bytes below 0x40 with the same background color at 0, 4, 8 and 12, each group of 4 reported on its own. Which palette goes with which art is not in the ROM: the palette within 8 KB of the art in only 15% of the Genesis cases measured, and a smoothness score picked degenerate palettes, so there is no automatic coloring. The tile sheets are colour mapped TGA files in grays (4 times smaller than before); the app decodes colour mapped TGA and the entry menu has "Use as palette for previews" (command line: `--palette=NAME`), which replaces the map of the previews with a `.pal` entry of the archive. A block of palettes that starts with black has an ambiguous start (zero padding before it is a valid prefix). Final Fantasy VI's LZSS (`DecodeLzss`, `compressed/lzss_*`): the format was read from the game itself, with no document. Tables of 3 byte addresses whose entries are stored one after the other give blocks of known size (the next address is this one plus the size in the first 2 bytes), and the blocks of two such tables parse exactly with one flag convention and decode to whole tiles with one reference layout only: a 16 bits size that counts itself, flag bytes from the lowest bit (1: a literal, 0: a reference of two bytes), a ring of 2048 bytes starting empty and written from 0x7DE, a reference = ring position (first byte and low 3 bits of the second) and length = (5 high bits) + 3; a wrong start of the ring corrupts the pictures, which is how 0x7DE was chosen. Nearly any bytes parse as LZSS, so a ROM only gives streams when the table relation holds (the next address equals this address plus the size): 61 in Final Fantasy III (USA), the same in its two other versions, none in Super Metroid, Zelda 3, Mario World or Chrono Trigger. Records with a length in front also line up (Super Loopz, Live A Live: 12 and 6 "streams" that decode to specks), so the median entropy of the streams of a ROM must be at least 4 bits per byte (5.6 for the pictures of Final Fantasy VI, 0.7 and 2.7 for those). The two other tables of the game that look the same (header + 2 = distance) are not graphics but the sound sample banks of its sound program (BRR blocks after a size and a loop point), as in Chrono Trigger. Chrono Trigger's graphics: found as tables of 3 byte addresses (e.g. 0x6FE20, 37 blocks of about 3.7 KB, the header is the size of what follows it, a clear bit in the flag byte is a literal and the data parses exactly with 2 byte references) but the reference layout was not found: FF6's layout and the other layouts tried (11 and 12 bit offsets, absolute or relative, rings of 2 and 4 KB) give sizes that are not whole tiles and noise. Donkey Kong Country: no table of addresses with sizes was found, nothing tried. A small 65816 disassembler written for this (reading the routine of the game) did not find the routines by their constants (`AND #$07FF` and ring start values). Pending: other SNES schemes (Donkey Kong Country, Chrono Trigger, Mega Man X... each game has its own), Enigma/Comper/Saxman, music (the sequence data and drivers are game specific: SNES N-SPC, Mega Drive SMPS), Mega Drive DAC samples, NES sound, NES CHR in other containers. Chrono Trigger's packet LZ (`DecodeLzPackets`, `ScanSnesPackets`, `compressed/lzp_*`): written from the public description at the NESdev wiki ("Tile compression") and checked against the game's tables of addresses (USA ROM: 436 streams, mostly 4096 bytes of 4bpp tiles, rendered as real pictures). A stream starts with the offset of the end of its first packet; masks are read from the lowest bit (0 literal, 1 two bytes: distance in the low 12 or 11 bits, length - 3 above); a control byte follows each packet (low 6 bits: bits of the next mask, 0 ends the stream; the first one tells the width: under 0xC0 12 bits). The last mask of a packet may run past the end offset, the control byte follows it. The scan keeps pointer runs whose entries decode and abut (next address = this one + bytes used). Still open: Donkey Kong Country (no public format description found, only community tools of unchecked license).

## Left on purpose (and where to find it: `git show legacy-v5:<path>`)

- The 11th Hour GJD needs `drv_default_d11d.dat`, built from the CD with `tools/d11dc`; Worms Armageddon DIR never worked in v5 (nothing to port).
- The small tools `dlngc`/`dlngcomp`/`dlngd` (language files of v5), `dlookc`/`dlookd` (themes), `dpackc`, `duppi`, `fngen`, `dus`: they belong to the plugin, theme and language systems of v5.
- `install/setup.iss` (Inno Setup): a reference for a Windows installer.
- HyperRipper reading HRF version 0 files, and the multi-thread scan (disabled in v5 too).
- The history files and the language files of v5.

Kept from `legacy/`: the HRF specification and the DUHTComp documentation (`docs/formats/`), the list of the names of the Westwood MIX files (`driver/data/mix_names.lst`).

## Checked and dropped

- **Progress callbacks of the driver** (`Dudi7_Init` host callbacks): measured and not worth it. The biggest real archive of the library (Boltgun, 5.6 GB, 112,081 entries) opens in 62 ms and the slowest Unity files (120 MB) in 180 ms, so there is nothing to report progress about while opening. The extraction already has progress as a job.
- **Direct copy by the host for formats with raw data** (`ExtractInternal=0`): extracting the 2,306 lumps of `DOOM.WAD` takes 0.66 s and is dominated by creating the files, not by the driver.
